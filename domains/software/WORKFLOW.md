# Software development and technical research: operating loop

1. **Intake.** Put new material in `inbox/`. Record where it came from and why it matters.
2. **Classify.** Choose project, source, session note, or memory proposal. Check sensitivity before importing more text.
3. **Contract.** Write the outcome, constraints, evidence, allowed tools, and acceptance checks.
4. **Retrieve.** Generate a scoped packet using `software` and the selected role. Inspect what was included.
5. **Work.** Architect frames the change → Builder implements or Debugger investigates → Reviewer checks behavior → Steward records validated findings and decisions.
6. **Review.** Check the original task, facts, evidence, assumptions, and any claimed execution.
7. **Remember.** Store only reusable conclusions as drafts. Review source accuracy and classification before activation.
8. **Close.** Save the result, next action, and review date. Archive completed project material according to your retention choices.

## When work crosses a boundary

Create separate task contracts. A software implementation for a business workflow belongs in software; its business objective and approved operating procedure belong in business. Pass the minimum reviewed requirements between them. Personal notes used to shape work preferences remain personal unless the owner chooses to share a sanitized preference.

## Stop conditions

Stop when the acceptance checks pass, when no new useful progress is possible without a specific missing input, or when the proposed work exceeds the selected scope. Return the exact unresolved question instead of an invented answer.
